3. LOCKED MATHEMATICAL INPUT
================================================================

Coordinates:
X = (T, x, theta, phi)

Index mapping:
0 = T
1 = x
2 = theta
3 = phi

Metric:

g_mu_nu = diag(
  -B*c^2,
  Rm^2/B,
  Rm^2*x^2,
  Rm^2*x^2*sin(theta)^2
)

D(x) = x^2 - 2*q*x + q
B(x) = D(x)/x^2

Domain:
q in [0.1, 0.9]
x >= 1
Rm > 0
c > 0
theta in (0, pi)

The metric is independent of T and phi.
The coordinate poles theta=0 and theta=pi are excluded from this chart;
they must not be described as physical curvature singularities.

The fixed Riemann convention is the one in
02_FULL_PIPELINE_CONTRACT_DATA_MODEL.txt:

R^rho_sigma_mu_nu =
partial_mu(Gamma^rho_nu_sigma)
- partial_nu(Gamma^rho_mu_sigma)
+ Gamma^rho_mu_lambda*Gamma^lambda_nu_sigma
- Gamma^rho_nu_lambda*Gamma^lambda_mu_sigma

Ricci contraction:

R_sigma_nu = SUM_rho R^rho_sigma_rho_nu

No implementation may change this sign convention or index order.

================================================================
4. RECONSTRUCTION ENGINE CONTRACT
================================================================

The engine input is a MetricJet containing only:

g[mu][nu]
dg[a][mu][nu]
ddg[a][b][mu][nu]

The engine must not receive:
- the archived analytical Ricci tensor;
- the archived analytical Einstein tensor;
- expected component values;
- a precomputed curvature tensor from the ORACLE.

The engine must reconstruct the output from the MetricJet.

Minimum module sequence:

1. InverseMetricEngine
   Input: g.
   Output: inverse metric g^mu_nu.
   Required check:
   SUM_sigma g^mu_sigma * g_sigma_nu = delta^mu_nu.

2. ChristoffelEngine
   Formula:
   Gamma^rho_mu_nu =
   (1/2) SUM_lambda g^rho_lambda *
   (dg[mu][lambda][nu] + dg[nu][lambda][mu]
    - dg[lambda][mu][nu]).

3. Derivative-of-Christoffel stage
   Uses the inverse-metric derivative identity:
   partial_k(g^rho_lambda) =
   -SUM_(a,b) g^rho_a * dg[k][a][b] * g^b_lambda.

   It also uses ddg to calculate partial_k(Gamma^rho_mu_nu).
   The implementation must document the index mapping explicitly.

4. RiemannEngine
   Uses the fixed convention in Section 3.

5. RicciEngine
   R_sigma_nu = SUM_rho R^rho_sigma_rho_nu.

6. RicciScalarEngine
   R = SUM_(mu,nu) g^mu_nu * R_mu_nu.

7. EinsteinEngine
   G_mu_nu = R_mu_nu - (1/2)*g_mu_nu*R.

8. ValidationEngine
   Runs algebraic and geometry-specific checks without modifying the
   reconstructed tensors.

Implementation may initially use the existing double backend only.
The API must keep the mathematical tensor contract independent of the
scalar backend so a future interval backend can be added without silently
changing index semantics.

================================================================
5. INDEPENDENT ORACLE BOUNDARY
================================================================

The ORACLE is a test-only reference path.

It must be isolated from the reconstruction engine at both source and
dependency level.

Required separation:

PRODUCTION / RECONSTRUCTION PATH:
MetricProvider -> MetricJet -> ReconstructionEngine -> computed tensors

TEST-ONLY REFERENCE PATH:
Locked metric written independently in a symbolic reference source
-> independent symbolic differentiation
-> independent Christoffel / Riemann / Ricci contraction
-> exact simplified reference expressions
-> test harness comparison

Rules:

1. The engine library must not include or link the ORACLE.
2. The engine API must not accept expected Ricci or Einstein values.
3. The ORACLE must not import, call, parse, or reuse MetricProvider code.
4. The ORACLE must not reuse the C++ engine's intermediate tensors.
5. The analytical III-B.3 target values may be used only by the
   test harness after reconstruction has completed.
6. The ORACLE source, symbolic tool version, exact input expressions,
   generated output and hashes must be preserved separately.
7. Separate source files alone do not prove independent derivation.
   The derivation path and its provenance must be inspectable.

Preferred first ORACLE:
A standalone symbolic derivation from the metric itself, using exact
rational parameters where possible and symbolic x, q, Rm, c, theta.
It must compute derivatives and contractions independently of the
C++ implementation.

A second independent check may use hand-derived component expressions.
Agreement between two implementations is useful evidence, but it is not
automatically a formal proof of the entire unbounded domain.

8. REQUIRED TEST REGISTER BEFORE ENGINE IMPLEMENTATION
================================================================

CURV-01 — Inverse identity
SUM_sigma g^mu_sigma*g_sigma_nu = delta^mu_nu.

CURV-02 — Christoffel lower-index symmetry
Gamma^rho_mu_nu = Gamma^rho_nu_mu.

CURV-03 — Riemann last-index antisymmetry
R^rho_sigma_mu_nu = -R^rho_sigma_nu_mu.

CURV-04 — First algebraic Bianchi identity
R^rho_sigma_mu_nu
+ R^rho_mu_nu_sigma
+ R^rho_nu_sigma_mu = 0
under the fixed convention.

CURV-05 — Ricci contraction consistency
Recompute Ricci directly from the stored Riemann tensor and compare
every component.

CURV-06 — Ricci symmetry
R_mu_nu = R_nu_mu.

CURV-07 — Ricci scalar
R = g^mu_nu * R_mu_nu = 0 for the locked metric.

CURV-08 — Einstein construction
G_mu_nu = R_mu_nu - (1/2)*g_mu_nu*R.

CURV-09 — Einstein trace
In four dimensions:
g^mu_nu * G_mu_nu = -R.

CURV-10 — Spherical symmetry
G_phiphi = sin(theta)^2 * G_thetatheta
for the diagonal locked metric.

CURV-11 — Independent symbolic ORACLE
Compare all Ricci and Einstein components against the separately
derived exact symbolic reference.

CURV-12 — Domain and failure behavior
Reject invalid metric inputs and report singular/non-finite inversion
or invalid numerical states without returning a false PASS.

The algebraic Bianchi identity and differential Bianchi identity are
different tests. CURV-04 is only the algebraic identity. The differential
identity requires covariant derivatives and is not included in this
minimum engine stage.

================================================================
9. KNOWN RISKS / FAILURE MODES
================================================================

A. Shared-formula risk:
If the provider, engine and test oracle copy the same component formulas,
agreement may be circular.

B. Convention risk:
A sign or index-order mismatch can produce plausible but incorrect
curvature components. The fixed convention must be tested explicitly.

C. Floating-point risk:
The double backend is diagnostic. It does not provide outward rounding,
validated enclosures or global error bounds.

D. Domain risk:
A finite set of test points does not certify the unbounded domain x>=1.

E. Coordinate risk:
The spherical coordinate poles are chart singularities. They must not
be interpreted as physical curvature singularities.

F. Reference-provenance risk:
An archived analytical target is not an independent ORACLE merely
because it is stored in a separate file.

G. Build-evidence risk:
The current provider test source exists, but CP-19 did not establish
a clean full build of all three registered tests at its exact snapshot.

H. Normalization risk:
C*r0^2 remains PENDING until the original definitions of C and r0
are recovered and checked. This engine design does not close it.
