5. HYPOTHESES AND UNRESOLVED TECHNICAL QUESTIONS
======================================================================

The earlier discrepancy remains:

- CAPD DoubleRounding::isWorking() returned 0 in the recorded
  optimized build.
- A manually sequenced rounding test returned the expected mode
  values in the recorded context.
- A build forced to actual O0 through a compiler wrapper returned
  CAPD_IS_WORKING_O0=1.
- The earlier O2 disassembly excerpt appeared unusually shortened,
  but the exact linked-binary control flow and relocation targets
  were not fully established.

Possible factors requiring discrimination:
- compiler transformations and floating-point environment assumptions;
- inline assembly constraints and clobbers;
- interaction between x87 control word and MXCSR;
- exact instruction set used by DoubleRounding::test();
- source/object/library mismatch or build provenance;
- behavior of the diagnostic itself.

None of these possible explanations is established as the cause.

Important technical distinction:
- ldmxcsr changes MXCSR, which governs SSE/AVX floating-point
  rounding control.
- fldcw changes the x87 control word.
- Evidence for one control register is not evidence for the other.
- -frounding-math must not be treated as a blanket proof that every
  compiler transformation respects every runtime floating-point
  environment change.
