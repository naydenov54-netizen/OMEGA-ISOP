5. MINIMAL RL PATH: INVESTIGATION TO VERIFIED RECORD
PURPOSE: Define one explicit route from research work to a grounded RL record, then keep validation, CE/CE-V decisions, and Volume V integration as distinct gates. No gate is automatic.

5.1 STAGE A - RL INVESTIGATION
Conduct the investigation in the Research Laboratory (RL). Define the question, objects, notation, domain, assumptions, and intended claim. Explore constructions, derivations, proofs, counterexamples, boundary cases, alternative interpretations, and failure tests as appropriate. Preserve meaningful negative results and unresolved questions. Do not describe an exploratory observation as an established result.

5.2 STAGE B - GROUNDED RL RECORD
When the investigation yields a result worth preserving, prepare a concise RL record using Section 6. The record must state the exact claim, record type/evidence class, definitions, domain, assumptions, derivation or reproducible method, checks performed and not performed, limitations, counterexamples/non-implications, provenance, Frozen Core compatibility, and current status. Record the result with its actual evidence status; do not upgrade it merely because it is written down or committed to GitHub.
An RL record may document a proved result, a conditional result, a computational finding, a negative result, a correction, or an unresolved boundary. The record must make that distinction explicit.

5.3 STAGE C - VALIDATION
Validate the specific claim against its own requirements. Check, as applicable:
- logical validity and whether the conclusion follows from the stated premises;
- consistency and precision of definitions, notation, types, and domain;
- completeness of the derivation or reproducibility of the method;
- boundary cases, degenerate cases, counterexamples, and failure tests;
- dependence on hidden assumptions or external premises;
- compatibility with protected OMEGA-ISOP architecture and Frozen Core;
- whether the stated evidence class and status match what was actually established.
Mark each check CHECKED, FAILED, NOT CHECKED, NOT APPLICABLE, or UNRESOLVED, with a short reason where material. A failed mandatory check requires correction or a status downgrade. An unchecked optional test does not invalidate unrelated work, but it must not be represented as completed validation.
Validation establishes only the scope actually checked. Mathematical validation does not by itself establish physical truth, empirical confirmation, literature novelty, or external registration.

5.4 STAGE D - CE / CE-V DECISION
After validation, make an explicit decision under the project's applicable CE/CE-V rules. Use the exact category and terminology defined by the current authoritative CE/CE-V records; do not silently treat the terms CE and CE-V as interchangeable if the governing records distinguish them.
The decision must be one of: ACCEPT WITHIN STATED SCOPE, RETURN FOR REVISION, REJECT, or DEFER WITH A NAMED DEPENDENCY, or the exact decision vocabulary required by the authoritative CE/CE-V procedure. Record the rationale, validation evidence, assumptions, scope, limitations, and traceability. Passing mathematical validation does not automatically confer CE/CE-V status. A CE/CE-V designation may be claimed only when the relevant authoritative record or procedure confirms that designation.

5.5 STAGE E - SEPARATE VOLUME V INTEGRATION ASSESSMENT

Determine whether the result is architecturally relevant, non-duplicative, compatible with the current hierarchy, sufficiently stable, and useful to the theory's development. Ask for the relevant Colab cell(s), source export, notebook section, execution output, or a user-provided verification snippet/code sufficient to identify the authoritative content. State the exact GitHub path and the exact disputed element. Do not repeatedly ask the user to re-verify the entire repository.
13.4 VERIFY IDENTITY BEFORE COMPARISON
Compare only corresponding artifacts whose relationship is established by exact path/name mapping, notebook/cell identity, version/provenance metadata, or an explicit user mapping. Where practical, record SHA-256, byte size, version, and source location. A SHA-256 match establishes byte identity, not provenance by itself. A SHA-256 mismatch alone does not establish corruption, invalidity, or which version is authoritative.
13.5 RESOLVE A CONFIRMED MISMATCH
When the user supplies the authoritative Colab source or verification code, compare the exact disputed GitHub artifact against it. If the comparison confirms that the GitHub artifact is an erroneous, obsolete, or unauthorized derivative, remove or replace only that exact GitHub path, preserving the authoritative Drive/Colab original. Prefer a narrow replacement when a corrected derivative is required; delete only when the file is genuinely extraneous and removal is the correct disposition. Record the source identity, comparison method, hashes where available, exact path changed, and resulting commit/readback.
13.6 DELETION SAFETY
Never delete a GitHub file based only on suspicion, filename similarity, date mismatch, formatting difference, or an unverified hash discrepancy. Before deletion, establish (a) the exact GitHub path, (b) the corresponding authoritative Colab/Drive source, (c) the material mismatch, and (d) why replacement or deletion is appropriate. Preserve unrelated files and all protected/Frozen Core records. If source identity or mismatch cannot be established, do not delete; report the specific uncertainty and request only the missing Colab evidence.
13.7 NO ROUTINE RE-SYNCHRONIZATION
Do not make the user repeatedly reconcile Drive and GitHub. Once a source-to-GitHub mapping and verification have been recorded for an artifact, reuse that verified mapping. Reopen comparison only when the artifact changes, a concrete inconsistency appears, or a claim-specific audit requires it.
13.8 REPORTING
For every reconciliation action, report separately: authoritative source supplied/identified; exact GitHub path; comparison performed; result; file action (none / replace / delete); commit SHA; and readback status. Never claim Drive/Colab verification if only GitHub was inspected.
13.9 OPERATING DEFAULT
Default to continuing from current verified project records. Do not perform historical archaeology. If doubt is material, request the exact Colab source or verification code, compare the corresponding artifact, and then correct only the confirmed GitHub derivative. Google Drive/Colab remains the original; GitHub remains the derived copy.
